## 0. Mission & non-goals

**Mission.** On startup, the desktop app (macOS + Windows) checks the latest
GitHub release for a newer version. If one exists, the lobby shows a
PT-styled affordance ("v0.9.0 is ready — update & restart"). Clicking it
drives the native updater (Sparkle on macOS, WinSparkle on Windows), which
downloads the existing release artifacts (DMG / Inno installer), verifies a
signature, installs, and relaunches the app. Zero new hosting: the update
feed (`appcast.xml`) is generated by the release workflow and attached to
each GitHub release; the app reads it via the stable permalink
`https://github.com/shubhamsinghshubham777/playtogether/releases/latest/download/appcast.xml`
(note: `/latest/` excludes pre-releases — that is desired).

**Approach (decided with the user 2026-07-31).** `auto_updater` 1.0.0
(leanflutter; wraps Sparkle on macOS, WinSparkle 0.8.1 on Windows) + drop the
macOS App Sandbox (the plugin requires it disabled; we are not App Store
distributed) + CI-generated signed appcast. Full research and rejected
alternatives (Velopack, desktop_updater, DIY) are in the 2026-07-31 session-1
§8 entry — do not re-litigate.

### Non-goals (DO NOT do these)
- **No Apple Developer ID / notarization** — user can't afford it now. The app
  stays ad-hoc signed; Sparkle's EdDSA archive signature is the trust anchor.
- **No Velopack / installer migration** — would orphan existing Inno/DMG
  installs and requires notarization on macOS.
- **No per-user Windows install migration** — stays admin/Program Files; one
  UAC prompt per update is accepted.
- **No custom Sparkle UI driver** — after our banner is clicked, the native
  Sparkle/WinSparkle dialog appears; that extra click is accepted.
- **No Linux updates** (no Linux releases exist).

## 2. Architecture as-it-is (verified against `main` 2026-07-31)

Distribution today: `build_installers.yaml` fans out to `build_windows.yaml`
(Inno Setup via inno_bundle → `PlayTogether-<v>-Windows.exe`, **admin install
to Program Files**, `[Registry]`/WebView2 patched in by
`.github/scripts/patch-installer-script.ps1`) and `build_macos.yaml`
(`flutter build macos` → **ad-hoc signed, un-notarized** DMG →
`PlayTogether-<v>-macOS.dmg`), then a release job publishes both with
`softprops/action-gh-release`, release name `v<version>`, tag
`v<version>_<run_id>`. Repo is public. macOS app is **sandboxed**
(`macos/Runner/*.entitlements`) — that sandbox is being removed by this work.
No updater code exists anywhere in `lib/`.

`auto_updater` 1.0.0 API (verified from source): `autoUpdater.setFeedURL(url)`,
`checkForUpdates({bool? inBackground})`, `setScheduledCheckInterval(int)`
(0 disables scheduled checks), `addListener(UpdaterListener)` with events
`onUpdaterError / CheckingForUpdate / UpdateAvailable / UpdateNotAvailable /
UpdateDownloaded / BeforeQuitForUpdate`.

Signing toolchain (verified from plugin source):
- **macOS**: Sparkle EdDSA. Keys via `fvm dart run auto_updater:generate_keys`
  (stores in Keychain; export for CI with `macos/Pods/Sparkle/bin/generate_keys -x <file>`).
  Sign: `macos/Pods/Sparkle/bin/sign_update <archive>` → emits
  `sparkle:edSignature="…" length="…"`. For CI, pass the exported key
  (`sign_update` supports a key-file/string flag — verify exact flag `-f`/`-s`
  with `sign_update --help` in the Pods checkout).
- **Windows**: WinSparkle 0.8.1 = **DSA-SHA1 via plain OpenSSL** (runs on any
  OS, incl. the ubuntu release job):
  - keygen (once): `openssl dsaparam 4096 > dsaparam.pem && openssl gendsa -out dsa_priv.pem dsaparam.pem && openssl dsa -in dsa_priv.pem -pubout -out dsa_pub.pem`
  - sign: `openssl dgst -sha1 -binary < FILE | openssl dgst -sha1 -sign dsa_priv.pem | openssl enc -base64` → value for `sparkle:dsaSignature` (WinSparkle ignores `length`; plugin tooling emits `length="0"`).

## 7. Robustness patterns to adopt

- Update-check failures are invisible to users + `reportNonFatal` — never a
  scary banner for an offline check (repo error-copy doctrine).
- The appcast permalink is additive infrastructure: a release published
  without an appcast asset silently stops updates (404 on the permalink
  resolves to the newest release WITH the asset only if same release —
  actually 404s). C2 makes generation unconditional in the release job so
  this can't happen; never make it conditional.
- Never log or echo private keys in CI; pass via env into the signing step.

### 2026-07-31 (session 2) — implemented A1–A2, B1–B6, C1–C3, D1–D3

**Verified against the built app, not assumed:**
- `codesign -d --entitlements :-` on the Release .app shows **no
  `app-sandbox`** — and dropping it needed *two* changes, not one: the
  entitlements files **and** `ENABLE_APP_SANDBOX = YES` → `NO` in all three
  `project.pbxproj` configs (Xcode-16-style build setting that re-injects the
  entitlement regardless of the file). §3 B2 only mentioned the files.
- `SUPublicEDKey` + `SUEnableAutomaticChecks=false` present in the built
  Info.plist; `Sparkle.framework` embedded with `Autoupdate` + `Updater.app`.
- `CFBundleVersion == CFBundleShortVersionString == 0.8.0` (Flutter mirrors the
  name when pubspec has no `+build`), and `package_info_plus` reads
  `CFBundleShortVersionString` on macOS / VERSIONINFO `ProductVersion` on
  Windows — which is *exactly* what Sparkle and WinSparkle each compare. One
  version value serves every appcast field. C2's "verify this once" is done.

**Corrections to §2/§3 — do not re-derive these:**
- `package_info_plus` is pinned **9.0.1**, not latest. 10.x needs win32 ^6;
  `livekit_client` → `device_info_plus` 12.x pins win32 ^5. Resolution fails
  otherwise.
- Sparkle is **2.9.3**. `sign_update` takes `--ed-key-file -` (key on **stdin**),
  so CI never writes the key to disk. `--verify` reads the *public* key from the
  Keychain, so it is useless on a runner — see the openssl route below.
- Sparkle's `edSignature` is a plain **ed25519 signature over the raw file**, so
  it can be verified with stock openssl against the shipped `SUPublicEDKey`
  (prefix the 32 raw bytes with DER header `302a300506032b6570032100`). Both that
  and the Windows DSA check now run in `.github/scripts/generate-appcast.sh`,
  which **fails the release** on a mismatch. All three failure paths (wrong DSA
  key, DMG changed after signing, version disagreement between jobs) were
  exercised locally and confirmed to exit non-zero.
- WinSparkle DSA is signed over the **double** SHA-1 (`SHA1(SHA1(file))`,
  confirmed in `signatureverifier.cpp`) and the base64 **must be unwrapped**
  (`openssl enc -base64 -A`) — the default wraps at 64 chars and a 4096-bit DSA
  signature is ~84, which would put a newline inside an XML attribute.
- `sparkle:os` is read **only as an `<enclosure>` attribute** by both. Sparkle
  ignores non-`macos` items; **WinSparkle falls back to the first item in the
  feed** when nothing is tagged `windows`, so tagging the Windows enclosure is
  load-bearing or Windows users get handed the DMG.

**Two things the plan did not know about (both now handled):**
1. **WinSparkle pops a native "Check for updates automatically?" dialog** from
   the app's *second* launch onward. `win_sparkle_init()` (which the plugin calls
   inside `setFeedURL`) writes `DidRunOnce` on the first run and calls
   `UI::AskForPermission()` on the next, unless the `CheckForUpdates` config
   value exists. The plugin never exposes
   `win_sparkle_set_automatic_check_for_updates`. Fix:
   `_silenceWinSparkleOwnChecks()` writes it with `reg.exe` before the first
   init, and the native updater is initialised **lazily on the banner click**,
   never at startup. The registry path derives from `Runner.rc`'s
   `CompanyName`/`ProductName` — renaming either silently brings the dialog back.
2. **WinSparkle relies on the app to quit itself.** `UpdateDialog::OnRunInstaller`
   launches the installer and *then* calls the shutdown-request callback, whose
   default implementation is literally "nothing yet". Without
   `onUpdaterBeforeQuitForUpdate` → `exit(0)` the installer races a live exe.
   macOS needs no equivalent; Sparkle drives quit-and-relaunch.

**Deviation from C3 (deliberate).** C3 asked to rewrite inno_bundle's `[Run]`
entry (drop `skipifsilent`, add `runasoriginaluser`) and "verify one entry serves
both paths". It does **not**: whether a `postinstall` checkbox entry executes
under `/SILENT` is not something the Inno docs promise. So
`patch-installer-script.ps1` now **leaves that entry alone** and appends a
`Check: RelaunchAfterSilentInstall` (`WizardSilent()`) twin carrying
`nowait runasoriginaluser`. Exactly one of the pair fires, and the script
**asserts the generated entry still carries `skipifsilent`** — that assertion is
what keeps the pair exclusive if inno_bundle ever changes. `installerArguments`
is `/SILENT /SP- /NORESTARTAPPLICATIONS`, the last one keeping Inno's Restart
Manager out of the relaunch so a single entry owns it.
(Trap found while writing that script: .NET regex `$` in multiline mode anchors
before `\n`, **not** before `\r`, so `[^\r\n]*$` never matches a CRLF-ended
`.iss` line. The pattern deliberately has no end anchor.)

**Also changed:** `PTBanner`'s activity dots moved from implicit-on-`.info` to an
explicit `showActivity` flag (the reconnecting banner passes it); the lobby's
`ListenableBuilder` now merges `UpdateService` with `ProfileService`;
`supportsSelfUpdate` added to `lib/platform.dart` (narrower than `isDesktop` —
auto_updater has no Linux impl); `.gitignore` now blocks the private-key
filenames Sparkle's/WinSparkle's keygen tools produce; `build/pt-instance-b.sh`'s
header comment corrected (bundle-id isolation is now the prefs domain, not a
sandbox container — the script itself still works unchanged).

**Known plugin wart (not hit by our flow):** `auto_updater_macos`'s
`willInstallUpdateOnQuit` delegate returns `true` but never calls
`immediateInstallHandler`, which would strand a *deferred/silent* install. We
only ever do user-initiated checks with UI, which does not use that path.
