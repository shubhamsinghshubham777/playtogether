# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

SyncTogether is a Flutter app for synchronized ("watch together") media playback across devices. Authenticated users (Google OAuth or anonymous guests) create/join **rooms** (6-char codes or `synctogether://join/<code>` invite links). Room size, session length, AV and what happens at expiry all come from the host's **tier** (guest / free / premium — see Entitlements & room lifecycle). Play/pause/seek/mode changes broadcast to all members over a private Supabase Realtime channel per room. Two playback modes: **local** files (media_kit) and **YouTube** (youtube_player_flutter). Rooms also have persisted chat with typing indicators and presence, ephemeral **quick reactions**, plus **voice/video facecams** via LiveKit.

## Setup & Commands

This project uses [fvm](https://fvm.app) to manage the Flutter SDK version — **always prefix `flutter` and `dart` commands with `fvm`** (e.g. `fvm flutter run`, `fvm dart run inno_bundle`).

A `.env` file must exist in the repo root before running or building — it is declared as a Flutter asset, so `flutter build`/`run` fail without it. Copy `.env.example` and fill in `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and optionally `SUPABASE_URL_LOCAL` + `SUPABASE_PUBLISHABLE_KEY_LOCAL` (see below), `LIVEKIT_URL` (facecams), `TURNSTILE_SITE_KEY` (guest-signup captcha), `SENTRY_DSN` (error reporting — omit it and reporting is disabled, which is normal for local work) and `POSTHOG_API_KEY` (+ `POSTHOG_HOST` only for EU/self-hosted projects; product analytics, likewise disabled when absent). **Never put server secrets in `.env` — it ships inside the app bundle.** A Sentry DSN and a PostHog *project* key are both write-only and public by design, so they belong here rather than under `supabase/` — a PostHog *personal* API key never does. Server-side secrets live in `supabase/functions/.env` and `supabase/.env` (gitignored; see `.env.example` files under `supabase/`).

```bash
# Full local dev ecosystem control
./scripts/dev.sh                        # Spin down previous state & spin up Supabase, Edge Functions & Web
./scripts/dev.sh down                   # Cleanly spin down all services & free ports
./scripts/dev.sh status                 # View running status of all components

fvm flutter pub get                 # install dependencies
fvm flutter run -d macos            # run (or: windows, android, ios)
fvm flutter analyze                 # lint (flutter_lints via analysis_options.yaml)
fvm flutter build macos --release   # release build per platform

supabase db push                    # apply supabase/migrations to the linked project
supabase functions deploy livekit-token
supabase secrets set --env-file supabase/functions/.env   # LiveKit API key/secret
supabase config push                # auth config (needs supabase/.env for Google OAuth + captcha secret)

# Website (Next.js 15 marketing & Paddle billing portal)
cd website && npm install
npm run dev                         # Next.js dev server at http://localhost:3000
npm test                            # Webhook deduplication & signature test suite
hookdeck listen 3000 synctogether-webhooks --path /api/paddle/webhook # Local Paddle webhook tunnel

gh secret set ENV_FILE < .env       # update the ENV_FILE repo secret CI writes .env from
```

**Debug builds point at the local Supabase stack, release builds at production.** `Env.supabaseUrl` prefers `SUPABASE_URL_LOCAL` whenever `kDebugMode` is set, so `flutter run` cannot quietly exercise migrations, RPC changes or destructive tests against the project real users are on. The guard is `if (!kDebugMode) return null` on a const, so release tree-shakes the branch away entirely and CI needs nothing in `ENV_FILE`. A debug build with no local values falls back to production, and the lobby wordmark reads `0.11.0 · local` in warning amber whenever the local stack is in use — a debug session that *looks* like production is the failure mode this exists to prevent. `.env` is a bundled asset, so **changing it needs a rebuild, not a hot reload**.

Desktop self-update needs two repo secrets, `SPARKLE_ED_PRIVATE_KEY` and `WINSPARKLE_DSA_PRIVATE_KEY` (see Self-update under Architecture). The release job fails loudly without them rather than publishing a feed nobody can install. Their public counterparts are committed; **the private keys exist only in those secrets and the user's password manager, and cannot be regenerated without orphaning every installed copy.**

To test room sync on one Mac, run instance A normally and instance B via `./build/pt-instance-b.sh` — instances of the same bundle id share one preferences domain (= one Supabase session), so the script clones the debug build under `app.synctogether.macos.b` to get a second identity. Re-run it after rebuilds; logs go to `/tmp/pt-b.log`. (The isolation used to come from the sandbox container; since the sandbox was dropped it comes from the bundle id itself, which is what `NSUserDefaults`/`flutter_secure_storage` key off either way.)

Test suites runnable locally and in CI:

```bash
fvm flutter test                    # Flutter Dart suite (test/)
supabase start && supabase test db  # RPC suite (pgTAP, supabase/tests/)
npm --prefix website test           # Website Node.js test suite (website/tests/)
```

`flutter test` needs a `.env` to exist even though no test reads it — the file is a declared Flutter asset, so without it the run dies at "Failed to build asset bundle" rather than on any assertion. The pgTAP suite runs each file as one transaction that rolls back, against the **local** stack only; it never touches a deployed project. `now()` is transaction-time in Postgres, so a test cannot observe a timestamp *advance* across statements in the same file — assert against a value you back-dated yourself instead.

Two seams exist purely so the sync layer is testable, and both are pure delegation — keep them that way. `lib/sync/sync_logic.dart` holds the decisions as free functions over plain values (authority election, gate evaluation, presence merge, last-action-wins ordering, the reaction throttle, the chat fuzzy-merge); `SyncService` delegates to it and re-exports it, so consumers still import only `sync_service.dart`. `lib/sync/sync_backend.dart` narrows everything `SyncService` needs from Supabase and media_kit to one `SyncBackend` interface (plus `SyncChannel`/`SyncPlayer`), defaulted to the real implementations — which is what lets a test drive a room with no network and no `Player`. `SyncChannel` deliberately mirrors `RealtimeChannel`'s method shape so the call sites read unchanged. Dev deps carry `fake_async` for the timer-driven tests (reconnect backoff, the state-request retry, the 100 ms settle window).

CI (`.github/workflows/`) is otherwise manual-trigger only (`workflow_dispatch`) and builds installers: Windows via `dart run inno_bundle` + Inno Setup (configured in pubspec.yaml under `inno_bundle:`), macOS via DMG. CI uses Flutter 3.44.8 and writes `.env` from the `ENV_FILE` secret. `build_windows.yaml` and `build_macos.yaml` hold all the per-platform build logic and are dual-triggered (`workflow_dispatch` + `workflow_call`); `build_installers.yaml` just calls both (`secrets: inherit`) and adds the GitHub release job — so the Flutter version, artifact names, and packaging steps each exist in exactly one place. Their `concurrency` groups carry a `-windows`/`-macos` suffix on purpose: inside a called workflow `github.workflow` resolves to the *caller's* name, so without it the two platform jobs would share one `cancel-in-progress` group and cancel each other.

## Conventions

- Dependency versions in pubspec.yaml are **exact pins** (no `^` ranges) — keep it that way when adding/updating dependencies.
- The code uses Dart's dot-shorthand syntax for enum/static access (e.g. `mainAxisSize: .min`, `_mode = .local`) — requires the pinned SDK; follow this style.
- App version lives in pubspec.yaml `version:`; CI extracts it for installer names.
- **Design system**: dark mode only. All colors/typography come from `lib/ui/pt_theme.dart` (violet glass aesthetic; fonts Space Grotesk / Outfit / JetBrains Mono bundled in `assets/fonts/`; icons via `material_symbols_icons`). Screens must not hardcode hex values — extend `PTColors`/`PTText` instead. Reusable widgets: `lib/ui/` (GlassPanel, PTButton, PTIconButton, PTSlider, PTCodeInput, PTAvatar, PTBanner, PTLoader, showGlassDialog…). Spinners are **`PTLoader`** (`lib/ui/loader.dart`) — a `CupertinoActivityIndicator` sized by a single `size` and tinted `PTColors.primary` by default; never `CircularProgressIndicator`. The one exception is the *determinate* countdown ring on `PTBanner`'s dismiss button, which has no Cupertino equivalent.
- Error copy is friendly/casual ("Hmm, that doesn't look like a YouTube link."), never raw codes. The corollary is that the *real* cause has to leave by another door: `lib/diagnostics.dart` has `reportNonFatal` (routes through `FlutterError.reportError`, which Sentry's `FlutterError.onError` picks up) for recovered failures, and `trace` for breadcrumbs on flows we expect to debug remotely. Breadcrumbs only transmit alongside a captured event, so instrumenting a happy path costs nothing. Both no-op without `SENTRY_DSN`. A `catch` that shows friendly copy and reports nothing is the pattern that made the Windows guest-login failure invisible for as long as it was — the one exception is the captcha dialog, which also prints Cloudflare's error code on screen, since whoever hits it is rarely whoever reads the dashboard.
- **Instrument as you go — this is a standing instruction, not a one-off pass.** Whenever you write new code on a distributed or asynchronous flow, *or touch existing code that has no instrumentation yet*, add it in the same diff: `reportNonFatal` in any `catch` that would otherwise swallow a consequential failure (never `debugPrint`, which is invisible in release), and `trace(msg, category:, data:)` at the transition edges — with the values the decision turned on in `data:`. Categories in use: `sync`, `gate`, `media`, `room`, `av`, `deeplink`, `auth`, `turnstile`, `youtube`, `tls`, `webview`. **Log transitions and corrections, never ticks**: no `trace` in `build()` or any per-frame path, and none on the 10 s position heartbeat, presence syncs, typing, reactions or scrub previews — those flood the breadcrumb ring buffer and evict the trail that matters. Never log chat message content or full local file paths; basenames, user ids, room ids, positions and durations are fine. Expected outcomes stay quiet — a mapped `RoomErrorCode` is a normal answer, so only its `unknown` fallback gets `reportNonFatal`.
- **Analytics is a separate doctrine from instrumentation, and the two must not be confused.** `trace`/`reportNonFatal` answer *why did this break*; `Analytics.track` answers *is anyone doing this*. Diagnostics may fire wherever a decision is made; a product event may fire **only where a human caused it**. See the Analytics section under Architecture before adding an event.
- **Splash sound**: `assets/sfx/splash.wav` is synthesised by `tool/generate_splash_sound.py` (stdlib only, no deps) — riser → impact → bell tail. It's build output: regenerate with `python3 tool/generate_splash_sound.py` and edit the script, never the wav. Whatever occupies that path must keep its transient at 0.30 s (see the splash notes under Architecture). Playback reuses media_kit — deliberately no new audio dependency, since `MediaKit.ensureInitialized()` has already run by then.
- **Reaction emoji**: `assets/emoji/*.json` are build output — Google's Noto Animated Emoji (Lottie), fetched and SHA-256-verified per file by `tool/fetch_reaction_emoji.py` (stdlib only). Refresh with `python3 tool/fetch_reaction_emoji.py`; edit the script, never the JSONs. They are **CC BY 4.0**, which is why README carries an attribution line — keep it if the set changes. The CDN path says `latest`, so a digest mismatch usually means Google republished rather than anything sinister: re-pin deliberately via `--print-digests` after eyeballing the size/frame-count delta it reports. The script also refuses to write if `lib/rooms/reactions.dart` and its own manifest disagree, because that list is simultaneously what ships and what the receive-side allow-list trusts — a set that drifts renders a hole for an emoji the sender considers valid.
- **CA bundle**: `assets/ca/cacert.pem` is build output — curl.se's distribution of Mozilla's root program, fetched and SHA-256-verified by `tool/update_ca_bundle.py` (stdlib only). Refresh with `python3 tool/update_ca_bundle.py`; edit the script, never the .pem. It needs refreshing occasionally as roots expire, but staleness is not urgent: the roots are *added* to the platform's, so an out-of-date bundle degrades to "the OS decides" rather than breaking connections. See the `lib/tls.dart` notes under Auth.
- **App icon**: source art in `assets/icon/` is generated, not hand-drawn — `tool/generate_app_icon.py` (needs `fonttools` + `rsvg-convert`) rebuilds the lobby `_Wordmark` tile as SVG, lifting the `Icons.play_arrow_rounded` outline out of the MaterialIcons font so the icon can't drift from the on-screen logo. Regenerate with `python3 tool/generate_app_icon.py && fvm dart run flutter_launcher_icons` (config in pubspec.yaml under `flutter_launcher_icons:`); edit the script, never the PNGs. The script also writes the multi-size `windows/runner/resources/app_icon.ico` itself — flutter_launcher_icons' Windows generator is off on purpose because it emits only a 256px frame. **Every platform's art is full-bleed** — iOS, macOS 26+ and Android adaptive icons all apply their own corner mask, and macOS 26 in particular treats a padded or alpha-bearing icon as legacy and drops it onto a default grey container (that's the grey border it used to show). Only Windows and pre-adaptive Android launchers, which never mask, get art that draws its own rounded corners. To see what macOS will actually render, ask it: `NSWorkspace.shared.icon(forFile:)` on the built `.app` — but IconServices caches per path, so flush with `rm -f "$(getconf DARWIN_USER_CACHE_DIR)com.apple.IconServices/store.index" && killall Dock Finder` or point it at a fresh copy.
- **Communication & Formatting (MANDATORY)**: **NEVER use LaTeX math formatting** (no `$`, `$$`, `\text{}`, `\frac{}`, `\times`, `\mathbf{}`, `\approx`, etc.) in chat responses, plans, or documentation. Always use clean plain text, standard math operators (`x`, `÷`, `=`, `~`), percentages, and readable markdown tables so text is directly legible in any markdown viewer.

## Architecture

Startup (`lib/main.dart`): dotenv → (Sentry, if `SENTRY_DSN` is set) → MediaKit → Supabase → analytics → `MaterialApp.router` with go_router (`lib/app_router.dart`). Everything after dotenv lives in `_bootstrap`, which Sentry runs as its `appRunner` so the whole app sits inside its error zone; without a DSN `_bootstrap` is simply called directly. Routes: `/login`, `/lobby`, and — **nested under `/lobby`** — `/lobby/profile`, `/lobby/subscribe`, and `/lobby/room/:id`; a redirect keeps signed-out users on `/login`. The nesting is load-bearing: it keeps the lobby page underneath, so every `context.go('/lobby')` (back buttons, leave, end room, eviction) shrinks the page stack and plays the *pop* transition — as sibling top-level routes `go` swaps the whole stack and Flutter animates a forward push instead. Build room paths with `roomPath(id)` / parse them with `roomIdOfPath` rather than hand-writing the prefix. Because the room now sits on a stack, `RoomScreen` wraps itself in `PopScope(canPop: false)` and routes a system back gesture through `_leaveRoom()` — a bare pop would skip `leave_room` and strand the membership. The media_kit `Player` is created once in `MainApp` and passed to `RoomScreen`; the room route keys `RoomScreen` by room id — go_router keys pages by route *pattern*, so it reuses the page for room A → room B, and without the key the old room's State would survive the navigation. `main.dart` also listens for `synctogether://join/<code>` deep links (app_links) **and** checks `getInitialLink()` — the native side replays the launch URL only to the first stream subscriber, which is supabase_flutter (it subscribes inside `Supabase.initialize`), so cold-start invite links never reach the stream listener. If signed out, the code is parked in `RoomService.pendingJoinCode` and consumed by the Lobby after login; if already in a different room, the old membership is left before navigating.

Desktop launches into OS fullscreen (`_enterFullScreen`, same `window_manager` switch the room's F/Esc toggle drives). It runs **after `runApp` and awaits `endOfFrame`**: asked any earlier, macOS's `toggleFullScreen` on a window the engine has not drawn into leaves the app with no window at all — frontmost, zero `AXWindows`, nothing on screen — instead of a fullscreen one. The call is unawaited and self-contained in a try/catch, so a window manager that refuses (headless or exotic Linux) costs a report rather than the app. `RoomScreen` seeds `_fullscreen` from `windowManager.isFullScreen()` in `initState` for the same reason its `WindowListener` exists: the listener only reports *transitions*, and the window is already fullscreen before the first room opens, so without the seed Esc would find nothing to exit.

`PTSplash` (`lib/ui/splash_screen.dart`) wraps the router child inside `MaterialApp.builder` — an **overlay, not a route**, precisely so redirects and the deep-link handler keep running underneath it and a cold-start invite arriving mid-splash still lands. Four things about it are load-bearing. The sound is `open`ed with `play: false` *before* the controller starts (racing a 450 ms budget) so media_kit's start latency falls outside the animation instead of inside it. The logo's `_Spring` curve peaks — its largest overshoot, which is the beat the ear reads as the hit — exactly on `_kImpact`, the same offset as the sting's transient (`IMPACT` in `tool/generate_splash_sound.py`); move one and you must move the other, and the tile's interval is *solved* against the spring's π/frequency peak, so retuning the curve retimes the animation. Scale and opacity run on separate intervals because a spring that faded across its whole travel would still be translucent when it lands. And the router child is mounted at `_prewarm`, ~300 ms *before* the fade starts, not at the fade itself: building the lobby's whole tree (glass blurs, shader warm-up) costs more than a frame, and paying it on the fade's first frame stalls the raster thread and turns the cross-fade into a visible cut — that was the original bug. Under reduce-motion the logo renders its end state and only the hand-off fade plays; the sting still sounds.

### Backend (`supabase/`)

Migration `…_multi_participant.sql`: `profiles` (auto-created by trigger on signup; guests get `Guest-xxxx`), `rooms` (code, `expires_at`, `ended_at`), `room_members` (role host/member), `messages` (chat, dies with room). All RLS-gated; room channels are **private** Realtime channels (`room:<id>`) authorized via `realtime.messages` policies. RPCs (`security definer`): `create_room` (code generation, tier-derived caps), `join_room` (expiry + `rooms.max_members`), `leave_room` (host succession → earliest joiner), `end_room` (host only), `get_server_time` (clock-skew-free countdowns), `delete_account`. `…_purge_stale_guests.sql` purges anonymous users older than 3 days daily and makes `rooms.created_by` cascade on user deletion (without it, `delete_account` and the purge fail for room creators). `supabase/functions/livekit-token` mints LiveKit tokens after checking room membership via the caller's JWT.

### Entitlements & room lifecycle (`…_premium_tiers.sql`, `lib/profile/entitlement_service.dart`)

Three tiers — guest / free / premium — decide room caps, AV, and what happens when a room runs out of time.

- **Limits are config, not constants.** `tier_limits` (tier pk; `max_live_rooms`, `max_members`, `max_session_minutes`, `max_total_session_minutes`, `av_level`, `persistent_room_cap`, `dormant_hours`, `free_extension_minutes`) seeded guest(1,4,60,60,none,0,0,0) / free(4,8,240,240,voice,0,24,60) / premium(20,16,240,1440,video,20,24,0). Tuning a tier is an `update`, not a deploy. `effective_tier(uid)` is `guest` for an anonymous profile, `premium` for an unexpired `subscriptions` row, else `free`; `my_entitlement()` returns the caller's row and is what `EntitlementService` reads.
- **The room owns its properties, not the joiner.** `create_room` denormalizes `max_members` / `av_level` / `persistent` / `dormant_hours` onto the `rooms` row from the **host's** tier. A free user joining a premium room gets 16-member, video-capable behaviour — per-seat rationing was considered and rejected as unequal in-room UX. `resume_room` re-stamps them from the resuming host's *current* tier, which is how a lapsed premium room quietly becomes a free-shaped one.
- **Expiry parks a room, it doesn't kill it.** `room_state(rooms)` is `live` / `dormant` / `expired`, and the per-minute `sweep_rooms` cron drives the transitions through `retire_room`: chat is wiped (session-scoped for every tier — deliberate), members are kept, and `resumable_until` is stamped `expires_at + dormant_hours`. `dormant_hours = 0` (guests) means deletion on the spot; `persistent` (premium) means no deadline at all. A persistent room whose owner has dropped off premium gets a one-time 7-day grace stamp instead of vanishing. `end_room` goes through the same `retire_room`, so "end room" and expiry cannot drift apart.
- **Client tier checks are affordance only.** Every cap is re-enforced in a `security definer` RPC, so a stale `EntitlementService` costs a worse error message, never a bypass. It falls back to the free-tier shape, which understates rather than overstates.
- **`extend_room` branches on config, never on the tier name.** `max_total_session_minutes > max_session_minutes` is "this tier picks its own length" (premium → duration sheet); otherwise `free_extension_minutes > 0` is the one-off teaser, spent via `profiles.free_extension_used`; otherwise `extend_not_allowed`. Reading the tier string here is how the free tier accidentally lost its freebie the first time.
- **The T-5 banner is where extending lives**, and it therefore **must not auto-dismiss for the host** — it is the only affordance, so retiring it after 10 s retires the feature. Members keep the auto-dismiss; they have nothing to act on.
- **An upsell offers the cheapest move the user can actually make, and for a guest that is not a waitlist.** `PremiumTeaseDialog` has two shapes, picked by whether `onSignIn` is non-null. Null is the *tease*: premium is not purchasable yet, so "Keep me posted" is genuinely all there is, and that's what the free tier's spent-freebie dialog and the lobby's room-limit dialog get. A guest is one Google sign-in from everything the dialog is describing, so theirs is a full-width `GoogleButton` on `AuthService.linkGoogleIdentity` — the same in-place upgrade the profile screen runs, keeping the user id and the session — with "Maybe later" beneath it. Offering a guest a premium waitlist was the original bug: it asked them to wait for a paid thing while a free one sat one tap away. The guest's perk list is free-tier-shaped for the same reason; listing 24-hour rooms and video facecams under "Sign in for more time" promises what signing in does not deliver. **`upgrade_cta_clicked` therefore carries `action: 'sign_in' | 'notify'`** — same event, same surfaces, so the funnel does not split, but the two intents stay separable. The lobby's room-limit dialog is waitlist-only because guests can't reach it (they raise `guest_room_limit` and get their own dialog); if that ever changes it needs the sign-in shape too.
- **Resume is client-driven, because paths are.** `rooms.media_position_ms` is written by `update_media_position` — **authority only**, on a 60 s timer plus play/pause/seek/mode-switch/leave, never the 10 s heartbeat. Local file *paths* are device-scoped and never leave the device: `lib/rooms/local_media_store.dart` keeps a `shared_preferences` map of room id → {basename, path, touched_at}, pruned against a fresh `list_my_rooms` plus a 35-day TTL. A trigger nulls the position whenever `media_updated_at` moves, so a resumed room can never seek the new video to the old video's position. The decisions are free functions in `sync_logic.dart` (`shouldAutoReopenLocalFile`, `resumeSeekPosition`) with Dart tests; the seek stands down the moment `SyncService.hasReceivedInitialState` is true, because the authority's answer beats our last durable write.
- **Positions are clamped where they enter, not where they are written.** media_kit reports a small negative position (`-41 ms`) right after `open()`, which `update_media_position` rejected with `invalid_position` on every room entry. `playablePosition` (`sync_logic.dart`, next to `resumeSeekPosition`) is applied at all three points where a player's position becomes `_position` — so the scrubber and `_skip` arithmetic are covered too, not just the write. The RPC deliberately still *raises* on a negative rather than coercing: a negative is nonsense, not a value with an obvious intent, and the guard plus its pgTAP coverage is what caught this one.
- **RLS on `rooms` is membership *or* ownership, and the `or` is why the lobby can see the room blocking a create.** The original policy was `using (is_room_member(id))`, so a creator who left could not `select` their own room at all. `list_my_rooms` is `security definer` and never noticed; `fetchLiveHostedRoom` is a plain PostgREST table read and got **zero rows**, which made `live` null and left both buttons of the guest-limit dialog silently doing nothing — no error, no log, because the null guards swallowed it. Any new direct read of `rooms` by an owner depends on this policy, not on the RPCs.
- **`end_room` accepts the room's creator as well as its acting host, but `delete_room` still does not.** A creator who left their own room was not a host-role member, so the "End that room" button in the guest-limit dialog raised `not_host` — the one action that frees their cap. The widening grants no new power: the creator can already `delete_room`, which is strictly more destructive (the row goes, versus retired-and-possibly-resumable). An acting host who merely inherited the room is unaffected and still never gets delete.
- **"End that room" ends *and then creates* — the create the user was refused is retried once.** The dialog exists only because `create_room` was blocked, so ending the blocker and stopping would leave them to press Create again for no reason; the copy already says "end it first", which implies the create follows. `_showGuestLimitDialog` therefore returns whether the room was actually ended, and `_create` retries with `isRetry: true` so a second refusal can never loop. The dialog's future is **not** the signal: `onEnd` pops before `endRoom` resolves, so the pending `Future<bool>` is captured and awaited after the dialog closes — reading the pop as success would retry into the same cap.
- **Both buttons in that dialog assume ownership, not membership.** `fetchLiveHostedRoom` finds the blocking room by `created_by`, so "Rejoin it" must go through `join_room` by code rather than `context.go(roomPath(...))` — Realtime authorizes the private channel on membership, so navigating straight in lands on a room whose channel cannot subscribe. `join_room` is idempotent for an existing member, so the same call serves both cases and repairs a hostless room on the way through.
- **A hostless room adopts its next arrival as host, and that rule is deliberately not creator-only.** `join_room` inserted `'member'` unconditionally, so anyone who left their own room and walked back in returned demoted — no `set_room_media`, no `end_room`, no kick, no transport lock. It is tier-blind, so guest, free and premium were all affected identically. The predicate is "does this room currently have a host", not "is this the creator": `leave_room` already promotes the earliest joiner, so a room only goes hostless when it empties, and `kick_member` raises `cannot_kick_host` rather than creating one. **Restoring host to the creator instead would let them take the room back off an heir who inherited it**, which contradicts the succession model — the creator's retained power is `delete_room`, not the host role. The already-a-member branch heals the same way, so an existing member of a hostless room is promoted rather than left stranded.
- **`list_my_rooms` lists what you own *or* belong to, and that disjunction is load-bearing.** The cap in `create_room` counts by `created_by`, so a membership-only listing let the two disagree: leaving a room you created drops the `room_members` row, the room vanishes from "Your rooms", and it still blocks you creating another. For a guest (`max_live_rooms` 1) that is a dead end — they cannot re-enter it, cannot reach the creator-only `delete_room`, and do not know the 6-char code, so they are locked out until it expires. The row therefore carries **`is_member`** alongside `is_owner`: a non-member cannot open the room directly, because Realtime authorizes the private channel on membership, so the lobby re-joins by code first. Ordering is `live` first then `created_at desc` — newest room on top, since `expires_at desc` sorted a fresh 5-minute room *below* a long-running one.
- **Adding a column to `list_my_rooms` means dropping it first.** Postgres refuses `create or replace` on a changed return type, and a `drop` takes the grants with it — so the migration must re-`grant execute ... to authenticated` or the RPC goes invisible to every client. That is the trap `07_grants_test.sql` exists to catch.
- **Deleting a room is the creator's power alone, and host succession does not hand it over.** `delete_room` checks `rooms.created_by`, not the `host` role — an acting host who inherited the room can `end_room` (end the session) but never delete it out from under the person who made it. `list_my_rooms` returns a server-computed `is_owner` so the lobby renders the affordance from the same fact the RPC enforces, rather than inferring it from the role.
- **The deletion broadcast comes from Postgres, not the client.** Realtime authorizes a private channel at *subscribe* time, so removing rows never ejects anyone — the same reason `kick_member` needs its `member_kicked` broadcast. `announce_room_ended` calls `realtime.send` on `room:<id>` **before** the delete, so members still watching are evicted rather than left on a room whose row is gone. It has to be server-side: whoever deletes the room is standing in the lobby, not subscribed to its channel. `end_room` goes through it too, which is what finally closes the same hole on the lobby's "End that room" button. Failure only `raise warning`s — the user asked for the room to go, and it goes.
- **`room_ended` carries a `reason`.** `deleted` gets "this room is gone" copy; anything else (including a payload from a client that predates the field) keeps the session-over copy, which for a dormancy-capable room is "waiting in your lobby". Getting this backwards tells someone their room is recoverable when it no longer exists.
- **The lobby's reload-on-exit edge is committed before it fires, and that ordering is load-bearing.** The room route is *nested* under `/lobby`, so `_LobbyScreenState` is alive and listening the whole time someone is in a room; `_evictSelf` → `noteRoomExited()` notifies it synchronously. `RoomService.loadMyRooms` then notifies again *before its first await* to raise `loadingMyRooms`, which re-enters the very listener that called it. With the "were we in a room" flag assigned after dispatching the reload, that re-entry still saw the old value and reloaded again — an unbounded recursion that froze the app (`StackOverflowError`, ANR, ~70k in-flight `list_my_rooms` requests) on every "End room for everyone". `RoomExitEdge.observe` (`room_models.dart`) exists to make the order impossible to get wrong: it commits the new state *before* returning true. `loadMyRooms` also only notifies when `_loadingMyRooms` actually flips, so a notifier that has nothing new to say stays quiet — the same defence one layer down.
- **Billing & Subscriptions (Paddle Merchant of Record)**: Premium subscriptions are processed via Paddle on the web (`website/components/PaddleCheckout.tsx`, `@paddle/paddle-js`).
  - **Webhook processing (`website/app/api/paddle/webhook/route.ts`)**: Paddle sends subscription events (`subscription.created`, `subscription.updated`, `subscription.activated`, `subscription.canceled`, `subscription.past_due`, `subscription.paused`). Webhooks verify the HMAC-SHA256 signature using `PADDLE_WEBHOOK_SECRET_KEY` via `@paddle/paddle-node-sdk`.
  - **Deduplication & Idempotency**: Webhook logic queries the existing `subscriptions` row by `user_id` and checks whether `status`, `current_period_end`, and `tier` are identical before issuing any update (`website/tests/webhook_dedup.test.ts`), avoiding redundant writes and spamming realtime channels.
  - **Cancellation (`website/app/api/paddle/cancel/route.ts`)**: Authenticated cancellation request passes the user's JWT, verifies ownership against Supabase, and requests subscription cancellation at period end via Paddle API.
  - **Realtime Reactivity (`20260816000000_subscriptions_realtime.sql`)**: `subscriptions` table is published to `supabase_realtime`. `EntitlementService` (`lib/profile/entitlement_service.dart`) automatically listens to `public:subscriptions:$userId` Postgres changes and runs a debounced (200ms) reload — immediately unlocking video facecams, 16-member rooms, 24h limits, and golden crowns without requiring an app reload or restart.
  - **In-App Subscription Screen (`lib/profile/subscription_screen.dart`, route `/lobby/subscribe`)**: Renders plan benefits, opens external browser checkout (`synctogether.app/premium` or `localhost:3000/premium` in debug mode), listens for `AppLifecycleState.resumed` to automatically trigger `_pollForSubscription()`, and plays celebratory confetti on activation.
  - **Local Development & Debug Grants**: Local debug builds can use the `debug_grant_premium(p_months)` RPC via `EntitlementService.instance.debugGrantPremium({int months})` (or raw SQL: `insert into subscriptions (user_id, tier, current_period_end) values ('<uid>', 'premium', now() + interval '30 days');`) to test premium features without external billing infrastructure.

**Premium has to be *visible*, not merely effective** — bigger rooms, video facecams and the extended reaction set are all capabilities that quietly work, so without a badge nobody knows they are premium and nobody in a room can tell who else is. The crown is `PTColors.premium`/`premiumBorder` (gold; the host pill stays `warning` yellow — a crown glyph and a "Host" pill are told apart by shape, not hue), rendered by `PremiumCrown` and the `GuestBadge`-shaped `PremiumBadge` in `lib/ui/identity.dart`.

- **`PTAvatar.premium` is an opt-in `bool`, and must stay one.** Doing it on the avatar covers the lobby pill, chat bubbles, the readiness roster, the overflow member list and facecam tiles in one place; letting the widget reach for `EntitlementService` itself would make it untestable and rebuild it on every unrelated notify. Whoever builds the avatar owns the lookup.
- **Other members' tiers come from `room_member_tiers(p_room_id)`, not from presence.** Presence was the cheap option and was rejected: it is self-reported, so any client could claim a crown. The RPC is `security definer`, membership-gated (a non-member gets **zero rows**, not an error — it is a cosmetic read), and answers the whole room in one round trip. `RoomScreen` caches the result in `_premiumMembers` and refetches only when a user id it hasn't resolved appears in membership or presence — **never per presence event**, which fires constantly. A lapse mid-session is not chased; the crown corrects on the next entry.
- **`effective_tier` is the single arbiter, which is what keeps guests crownless.** It short-circuits on anonymous accounts before it ever looks at `subscriptions`, so a guest with a stray subscription row still reads `guest`. The client decision is the one-liner `tierWearsCrown` in `entitlement_service.dart`; never re-derive it from a `subscriptions` read, which RLS makes owner-only anyway.
- **A crown is not an analytics event.** It renders; nobody caused it. Nothing here calls `Analytics.track`.

Anonymous sign-ins are captcha-gated: Cloudflare Turnstile is enabled server-side (`[auth.captcha]` in `config.toml`, secret via `supabase/.env`), and the client shows a "Quick check" WebView dialog (`lib/auth/turnstile_dialog.dart` — **`localhost` must stay in the Turnstile widget's hostname allow-list**). The challenge page is served from a throwaway `HttpServer` on the IPv4 loopback rather than loaded as inline data, because Windows silently discards `InAppWebViewInitialData.baseUrl`: the WebView2 backend routes initial data through `NavigateToString`, which takes no base URL and always produces an opaque origin, so Turnstile refused to issue a token and guest sign-in was impossible there. A real loopback origin is the one form every platform's webview agrees on — the YouTube embed (`lib/player/youtube/`) is served the same way. Binding a loopback server used to require `com.apple.security.network.server` in **both** entitlements files, because the macOS sandbox blocks `listen()` without it (loopback included) and a debug build would work while CI's DMG silently did not; **the sandbox is gone** now (see Self-update below) so that entitlement is inert, but it and the other sandbox keys are deliberately left in place so restoring the sandbox stays a one-key change. The client skips the dialog when `TURNSTILE_SITE_KEY` is absent from `.env`, but the server still requires a token, so guest login fails without the key configured.

Windows needs one more thing before that dialog can render at all, and it is set up in `lib/auth/webview_runtime.dart` (`PTWebView.init()`, called from `_bootstrap`): **an explicit `userDataFolder` under `LOCALAPPDATA`**. Left null, WebView2 defaults that folder to the directory holding the executable and tries to create `synctogether.exe.WebView2` beside it — which is under Program Files for the admin install inno_bundle configures, so a standard user token cannot write it and the environment fails to create. All that reaches Dart is `PlatformException: Cannot create the InAppWebView instance!`, and since it surfaces asynchronously from the platform view it lands as an *unhandled* error, leaving the dialog to sit on an empty box until the 20 s deadline. Passing `PTWebView.environment` to every `InAppWebView` is what keeps it writable. `init()` also probes `WebViewEnvironment.getAvailableVersion()` first: null means the runtime genuinely is not installed (the installer's Evergreen bootstrapper never took), which is a different fix and gets its own `webview2-missing` code and its own on-screen copy — "try again" is wrong advice for a missing OS component. A *failed environment creation* deliberately does not block the dialog; it reports and falls back to the plugin's default, since attempting the challenge beats refusing it.

### Auth (`lib/auth/`), Profile (`lib/profile/`), Rooms (`lib/rooms/`), Web App (`website/`)

`AuthService`: browser `signInWithOAuth(google)` + web redirect bridge (`https://synctogether.app/auth/desktop-callback` or `localhost:3000` locally) + `synctogether://auth-callback` deep link (declared in the Info.plist/manifest on macOS/iOS/Android; on Windows it is an installer concern — `.github/scripts/patch-installer-script.ps1` appends the `[Registry]` handler, so **the scheme only resolves in installed builds, never under `flutter run`**. Linux is still unregistered). The web bridge displays a "Login Successful" confirmation screen in the browser and automatically forwards the PKCE auth parameters to `synctogether://auth-callback`. Windows also needs the runner half: `windows/runner/main.cpp` calls app_links' `SendAppLinkToInstance()` first thing in `wWinMain`, because the OS delivers a URI by launching a *new* process with it as argv[1] — without the hand-off over WM_COPYDATA the callback signs a second, invisible instance in while the original waits forever. That makes Windows single-instance. `signInAnonymously` for guests, `linkIdentity` to upgrade guest→Google.

**Auth Redirect URLs in `config.toml`**: `additional_redirect_urls` is configured with `["http://localhost:3000/**", "https://*.vercel.app/**", "https://synctogether.app/**"]` so Google OAuth redirects work seamlessly across the web application, desktop callback bridge, preview deployments, and local dev server without conflicting with the native desktop/mobile URI scheme (`synctogether://auth-callback`).

**`enable_manual_linking = true` in `config.toml` is what makes `linkIdentity` exist at all, and the Supabase default is `false`.** With it off, gotrue answers `/user/identities/authorize` with **404 `manual_linking_disabled`** — not 403, not a validation error — so *every* guest→Google upgrade fails identically: the profile screen's "Sign in with Google", the room's expiry upsell, anything added later. It presents as `AuthException` inside the button's own `try`, so the friendly "Couldn't start Google sign-in — try again" fires and the advice is wrong, because no amount of retrying enables a server setting. It is an **auth config key, so it ships via `supabase config push`, not `db push`** — a local stack fixed by `supabase stop && supabase start` says nothing about production, and the two are separately deployed. Confirm which one a given stack has rather than assuming: `docker exec supabase_auth_synctogether env | grep MANUAL` locally, or probe `/auth/v1/user/identities/authorize?provider=google&skip_http_redirect=true` with any user JWT — enabled answers with an `accounts.google.com` URL.

**`AuthService.start()` (called from `_bootstrap`) must stay subscribed**, and its `onError` is the load-bearing half. supabase_flutter consumes the `auth-callback` deep link inside its *own* listener, so the code-for-session exchange runs nowhere near the sign-in button's `try`/`catch`; when it fails, `_handleDeeplink` hands the `AuthException` to gotrue's `notifyException`, which calls `addError` on `onAuthStateChange`. With no error handler attached that is an unhandled zone error — fatal in Sentry and *nothing whatsoever* on screen, which is how a TLS failure on one Windows box presented as Google sign-in silently doing nothing. Errors are promoted to a user-facing snack (via the `failures` stream, which `MainApp` renders) only inside the OAuth window `_startOAuth` opens: the same stream also carries routine background token-refresh failures, and snacking or reporting each of those is the noise that trains people to ignore both. `_startOAuth` also checks the `bool` that `signInWithOAuth`/`linkIdentity` return — `launchUrl` reports a missing browser by returning false rather than throwing, so that path was silent too.

`lib/tls.dart` (`installTlsOverrides()`, awaited first thing in `_bootstrap`, before anything opens a socket) does two things. It installs Mozilla's root program from `assets/ca/cacert.pem` — because `CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate` on Windows traces to Dart snapshotting the Windows ROOT store instead of building chains through CryptoAPI, so roots Windows would install on demand never arrive (dart-lang/sdk#52266, open). **The bundle is added to the platform's roots, never substituted for them**: `withTrustedRoots: true` is what preserves every root the machine itself trusts, including the private CA a corporate TLS-interception proxy installs — replacing them would fix the reported failure and break every managed network in exchange. That additive shape is also why a stale bundle cannot regress anything; it just stops contributing. A failed asset load reports and leaves the context null, which is precisely the old behaviour. Second, its `badCertificateCallback` **reports and still returns false** — it changes nothing about which handshakes succeed, and returning true is exactly what an interception proxy needs from us. The callback receives the certificate verification *stopped on* — the unchainable root or intermediate, not the leaf — which is what still discriminates a chain even Mozilla's roots cannot complete from an interceptor whose issuer is private by design. Supabase serves leaf → GTS WE1 → GTS Root R4 cross-signed by GlobalSign Root CA; a report naming those is a chain we should have built, anything else never reached Supabase. Reports dedupe per host+issuer per run because Realtime reconnects with backoff. `ProfileService`/`RoomService` are ChangeNotifier singletons wrapping the tables/RPCs; `RoomService.serverNow` applies the `get_server_time` offset — always use it for expiry math. `RoomService` also wraps the lifecycle RPCs (`loadMyRooms`/`extendRoom`/`resumeRoom`/`deleteRoom`/`updateMediaPosition`) and holds `myRooms` for the lobby's live-and-dormant list. `RoomScreen` (`lib/rooms/room_screen.dart`) is the room orchestrator: owns playback mode state, countdown/T-5 warning/eviction ("That's a wrap!" popup), banners (reconnecting, file mismatch), chat panel, facecam rail, overflow menu (member list, copy invite, leave, end room), desktop + portrait + landscape layouts.

### Sync layer (`lib/sync/`)

`SyncService` is room-scoped: created on room entry with `(player, room, profile, role)`, disposed on leave. It broadcasts typed events (`sync_events.dart`): play/pause/seek, `state_request`/`state_response`, `mode_switch`, `chat`, `typing`, `position_sync` (host heartbeat every 10 s; members correct if drift > 1.5 s), `file_info` (local-file identity for mismatch banners), `room_ended`.

- **Echo/loop prevention** — three mechanisms, do not break them: channel `self: false`; `_isApplyingRemoteAction` flag (reset after 100 ms settle); last-action-wins timestamp ordering (`_shouldApply`).
- **Late-joiner state sync**: only the **authority** answers `state_request` (host if present, else earliest-joined present member) — computed with the *requester excluded*, so when the authority is the one asking (a host reopening their own room) the next in line answers and there is still exactly one responder. Joiner retries once after 2 s then assumes idle. The entry response is answered while the joiner still has the file picker open, so its seek hits an empty player and is lost; `_checkSelfGateSatisfaction` therefore re-requests state on the edge where we *first* have the room's canonical media open. A playing room heals without this (the joiner shuts the gate, everyone pauses at a held position, the reopen seeks back to it) — a room that was already paused broadcasts nothing at all, which is how a late joiner used to end up parked at 0. The resync is skipped when `_roomPlaying`/`_pausedByGate` (the gate resume owns the realignment) or when we're alone.
- **Presence**: `Stream<List<PresentMember>>` keyed by `user_id` (multi-device users count once); payload carries display name/avatar/role/membership `joined_at` (feeds authority election). Host succession re-tracks presence via `updateRole`.
- **Presence is budgeted against the server's real contract: 5 calls per 30 seconds.** Realtime answers a client that tracks too fast with `Client presence rate limit exceeded` and drops the **whole channel** — sync, chat and the readiness gate with it. The limit is `CLIENT_PRESENCE_MAX_CALLS=5` over `CLIENT_PRESENCE_WINDOW_MS=30000` (realtime's `runtime.exs`; unset in `config.toml`, so the defaults apply — and the tenant's generous `max_events_per_second: 100` is a different counter entirely). **It is a per-30-second budget, not a per-second rate** — a plain sub-second coalescer caps the instantaneous burst, still allows a sustained 2/s, and gets dropped anyway. Confirm it at the source rather than inferring it: `docker logs supabase_realtime_synctogether | grep ClientPresenceRateLimitReached`.
- **`_presenceThrottle` therefore has three parts, and all three are needed.** `TrailingThrottle` (the generalised `ReactionThrottle`, now a `typedef` of it) carries a 2 s coalescing `interval`, a hard `maxCalls`/`window` budget of 4-per-30 s (one under the server's 5, for headroom), and a `presencePayloadsMatch` dedupe. **The dedupe is what makes the budget survivable**: opening a dialog churns readiness `none -> selecting -> none`, which nets to no wire change at all, and without dedupe those no-op flips burn the budget and defer the `ready` that actually opens the gate by up to 30 s. A redundant submit also *cancels the pending queue*, since the stale queued value has been superseded by one that already matches the wire.
- **It coalesces, never drops.** Presence *is* the gate, so a lost final state strands the room behind the waiting overlay forever; `fake_async` covers "the last state always flushes" at both the throttle and `SyncService` level, plus "no 30-second window ever exceeds the budget" over a 100-second churn. Throttling the wire cannot affect our own gate decisions — `_selfPresence` is built from local fields, not from the presence state.
- **A resubscribe calls `renew()`, which is not the same as clearing the throttle.** A fresh channel's presence state is *empty*, so the re-announce must go out even though the payload is unchanged (`renew` drops the dedupe memory) and must not wait out a coalescing window opened on the dead connection (`renew` waives the spacing). It deliberately **keeps the budget** — the server counter is keyed on the JWT `sub`, so it may well survive the reconnect, and reconnects back off >= 1 s anyway.
- **`joined_at` falls back to a cached timestamp, never a fresh `DateTime.now()`.** A recomputed fallback differs on every call, which would defeat the dedupe entirely on any client whose membership row has not loaded yet.
- **Chat**: rows in `messages` are durable history (loaded on entry, reloaded + fuzzy-merged after every reconnect — broadcasts don't replay); the broadcast is only low-latency fan-out.
- **Reconnection**: on channel error/close, exponential-backoff resubscribe + fresh `state_request`; `connectionStream` drives the "Reconnecting…" banner. Subtlety: `unsubscribe()` reports `closed` back into the subscribe callback, so intentional teardown (`disconnect()`, reconnect cycles) must not be mistaken for a drop — that's what `_tearingDown` and the `identical(channel, _channel)` check guard; removing them recreates an infinite reconnect loop and evicted clients re-joining dead rooms.
- **Dual-player routing**: `RoomScreen` sets `onRemotePlay/Pause/Seek` (+ `onRemoteDriftCorrect`, which must NOT pause YouTube) to route remote actions to the active player, and must call `updatePlaybackState(mode, youtubeUrl)` on mode changes. Every user-initiated play/pause also broadcasts a seek to keep positions aligned. Remote `mode_switch` must dismiss open source/URL dialogs (URL dialog first — it sits on top) without tripping the "re-ask when cancelled" fallback.
- **YouTube runs on our own IFrame bridge** (`lib/player/youtube/`), not a package — `youtube_player_flutter` had no Windows implementation and no upstream movement. `PTYouTubeController` serves an IFrame Player API page from a throwaway loopback `HttpServer` and drives it through `flutter_inappwebview` (the Turnstile origin doctrine, for the same reason: Windows drops `InAppWebViewInitialData.baseUrl`, so `loadData` yields an opaque origin the IFrame API can't post back to — never "simplify" it to inline HTML). Windows also needs `--autoplay-policy=no-user-gesture-required` on the WebView2 *environment* (`PTWebView.init`), because `mediaPlaybackRequiresUserGesture` is Android/iOS/macOS-only and nothing ever touches the page — the room's transport is Flutter widgets. `PTYouTubeEmbed` is a display surface only: keep the `IgnorePointer` around it and `pointer-events:none` in the page, or the embed's own play button becomes a way around the readiness gate and the transport lock.
- **YouTube intent model** — do not "simplify" this away: iframe state transitions land 200–500 ms after commands, far outside the 100 ms settle window. `_ytIntendedPlaying` in `RoomScreen` is the agreed play state: seeks restore it afterwards (`_ytSeekKeepingPlayState`, with a short event-suppression window for the play blip), the player listener only broadcasts transitions that *diverge* from it (direct iframe clicks), and remote commands arriving before the iframe is ready are queued and flushed on the first ready tick (late-joiner sync). The forced `play()` on seek was the package's, and is gone — but the pause-restore stays, because the IFrame API only preserves pause for a player that has *started* and seeking a `cued` one does begin playback. Changing video **reuses the controller** (`loadVideo` → `cueVideoById`, cue not load, so it stays idle and produces `cued`) rather than rebuilding the webview; the widget is still keyed by `ObjectKey(controller)`, **never by URL**, and `_switchToYouTubeMode` still early-returns on a same-video re-switch — duplicate `mode_switch` replays are routine after a reconnect, and resetting readiness for one shuts the gate on a room that never changed. YouTube readiness counts `cued` as loaded: the buffered fraction never rises for a member who hasn't pressed play, so a buffered-based check is unreachable for idle members. Duration comes from `getDuration()` at cue time (the old JS `_probeYtDuration` poll is gone — the bridge pushes it).
- **Known bug (accepted for now)**: the mouse cursor flickers over the room screen in YouTube mode on macOS — see `docs/known-issues.md` before attempting a fix; a Runner-level WKWebView swizzle was tried and reverted. The Dart-side `IgnorePointer` around the embed is not about this: it stops the platform view competing for input so taps reach our gesture layer — keep it.
- **Attribution toasts**: `SyncService.remoteActions` emits `RemoteAction` ONLY from the user-initiated play/pause/seek handlers. It must never be fed from `state_response` (which reuses `onRemoteSeek/Play/Pause` — would toast on late-join) or drift correction. Anything user-visible triggered by sync events must keep this user-initiated vs mechanical distinction.

### Room viewing UX (`RoomScreen` + `room_control_bar.dart`)

- **Keyboard/focus**: shortcuts are ignored while any `EditableText` has focus. Esc consumers are strictly ordered — text-field unfocus → reaction strip close → chat close → fullscreen exit — and new Esc handlers must slot into that order explicitly; whatever closes must hand focus back to `_shortcutFocus`.
- **Desktop single-tap on the video is intentionally instant**: no `onDoubleTap` on that gesture detector (double-tap recognition adds ~300 ms lag; a deliberate product call). Touch layouts get double-tap ±10 s skip zones instead; double-click-fullscreen was rejected for the same reason — fullscreen is F/Esc via `window_manager` (desktop only, gated by `lib/platform.dart`; a `WindowListener` keeps the flag synced with native green-button transitions).
- **Glass rendering trap**: wrapping `GlassPanel` in `Opacity` makes its `BackdropFilter` blur an empty layer — animate glass surfaces by sliding/clipping, never fading (see the chat panel's `_chatAnim`). A collapsed overlay in a `Positioned` still fills its slot (tight constraints) and eats clicks — wrap the zero state in `IgnorePointer`.
- **Broadcast on gesture end, preview locally during** (scrub `_dragValue` pattern) — never broadcast per-tick.

### Readiness gate (`lib/sync/` + `RoomScreen` + `readiness_overlay.dart`)

Nobody can start or scrub until **every present member** has the room's canonical media loaded. Strict lockstep: a member swapping files mid-play, or a late joiner, system-pauses everyone; when the gate reopens, playback auto-resumes at the held position.

- **Canonical media is room-level and host-only.** `rooms.media_kind/media_name/media_duration_ms/media_url/media_updated_at`, written solely by the `set_room_media` RPC (host + live-room enforced server-side; a `rooms_media_shape_chk` constraint keeps per-kind fields null). The row is the source of truth — it survives host succession and reaches late joiners; the `media_set` broadcast is only fan-out. Clients refetch the row on entry and on **every** resubscribe. `RoomMedia.isNewerThan` (keyed on the **server** clock `media_updated_at`, never `SyncEvent.timestamp`) stops a late-resolving refetch from clobbering a newer broadcast.
- **Readiness rides on presence** (`ready_status`, `loaded_file_name`), because presence replays to joiners and dies with the connection — a member who drops stops holding the gate shut. `retrackReadiness` mirrors `updateRole`. `ReadyStatus`'s declaration order IS its rank: the multi-device merge keeps the *most ready* device. Reconnect needs no extra code — `_readyStatus` survives, and the subscribe callback already re-tracks.
- **`ready` means "a file is open", not "the right file".** The name comparison lives in `memberSatisfiesGate`, which is what lets the UI distinguish "Loading" from "Wrong file (name)".
- **`gateState` is tri-state.** `indeterminate` until the first presence sync — render it as *usable*, never as closed, or every room entry flashes the overlay.
- **Only the authority emits derived actions** (`_evaluateGate`), else eight clients broadcast the same pause. The decision uses `_roomPlaying` (room-level), **not** `isPlaying` (our own player) — when the host opens a new file their player stops while everyone else plays on, which is exactly when the gate must pause. `_pausedByGate` is tracked on **every** client so host succession mid-wait doesn't lose auto-resume; any human play/pause clears it, so auto-resume never overrides a deliberate pause. The held resume position is dropped when *we* are the blocker (our position is about some other file).
- **Gate-derived play/pause carry `reason: 'gate'` and never raise attribution toasts** — that's the `remoteActions` user-initiated-only invariant.
- **"Start without them" is a per-member, per-media waiver, not a switch.** `waiveGateBlockers` (host only) names exactly who is holding the gate right now and broadcasts `gate_waiver`; `evaluateGateState` then treats those ids as clearing the gate. Anyone arriving *afterwards* shuts it again, which is the lockstep contract still doing its job rather than a bug. `_adoptCanonicalMedia` clears the set, because "start without Sam on this film" says nothing about the next one. `memberSatisfiesGate` keeps reporting the underlying truth, so a waived member still sees the overlay and their "Locate your copy" button while everyone else watches — which is why `_syncGateReveal` keys on `_selfBlocksGate` as well as `gateState`.
- **Every broadcast stamps itself via `_nextTimestamp()`**, never `DateTime.now()`. `_shouldApply` drops `timestamp <= _lastAppliedTimestamp`, and `_playPause` sends play *and* seek in one synchronous block — same-millisecond collisions silently ate the second event.
- **Transport lock** (`rooms.transport_lock`, `set_transport_lock`): host-only remote. Enforced at the same choke points as the gate.
- **Gate at the choke points, not the widgets** — `_playPause`/`_seek` (and `_skip` via `_seek`) cover keyboard shortcuts and double-tap skip zones, which never touch the control bar. `transportEnabled`/`transportHint` are affordance only.
- **Kick/ban**: `kick_member(room_id, target, ban)` + `room_bans`; the ban check in `join_room` sits *before* the already-a-member early return. Deleting the membership row does **not** eject anyone — Realtime authorizes at *subscribe* time — so the `member_kicked` broadcast is load-bearing.

### Quick reactions (`lib/rooms/reactions.dart`, `reaction_overlay.dart`, `reaction_strip.dart`)

Meet-style: a control-bar toggle opens a glass strip of 8 emoji; a tap renders an animated Noto emoji floating up over the whole room screen with a sender caption, and broadcasts on the existing private channel.

- **Ephemeral by design, like `typing`** — no row, no history, no replay. Reactions sent while you were disconnected are simply gone, and nothing about reconnection tries to recover them.
- **They must never touch the playback machinery.** `_handleReaction` does not go through `_shouldApply` — that advances `_lastAppliedTimestamp` and would silently eat the next real play/pause. It also never feeds `remoteActions`, which stays strictly user-initiated *transport* attribution.
- **Local echo is mandatory** (channel is `self: false`), and it is never throttled. The wire is: outgoing broadcasts are capped at one per 250 ms, with the excess *coalesced* rather than dropped — the last emoji in a burst still goes out, so tapping two different ones quickly doesn't lose the second. The cap exists because this channel also carries play/pause/seek.
- **The receive side allow-lists against `kAllReactions` — the whole manifest, bundled or not — and stays tier-blind.** An emoji is judged by whether we can *render* it, never by who is watching: a free viewer must still see a premium sender's 🍿. The **send** side is the tiered one, via `reactionAllowedForTier(emoji, SyncService.entitlementTier)`: below premium you send the bundled 8, premium sends the lot. Narrowing the receive side to the sender's tier is the mistake to avoid — it renders a hole for an emoji the sender considered valid.
- **Only the 8 bundled reactions ship in the app.** `kExtendedReactions` are fetched on demand from Google's CDN by `lib/rooms/reaction_cdn.dart` and **checked against a SHA-256 pinned in the manifest** before they are ever decoded; a mismatch is rejected permanently for the session and reported, so a republished-or-swapped animation degrades to the glyph rather than rendering. The cache is in-memory only — no `path_provider`, no disk-cache invalidation, and the cost is one small fetch per emoji per launch. Failures are a `trace`, not a `reportNonFatal`: being offline is the documented normal path, and the overlay already falls back to the glyph.
- **The strip stays eight cells at every tier**; the wider set is a *panel* behind a `+`, because the strip floats over the video inside a `FittedBox` and a 24-cell row would shrink every cell to nothing.
- **`tool/fetch_reaction_emoji.py` verifies both lists and bundles only `EMOJI`.** It cross-checks the codepoints *and* the extended digests against `lib/rooms/reactions.dart`, because the Dart copy is the one that actually guards the runtime fetch — a drift there fails silently at runtime (flat glyphs), so the script is the only place it is visible. Run it when reactions start rendering flat.
- **Never gated.** Not by the readiness gate, not by the transport lock, in the UI or at the send path — expression is not transport, so a room that can't press play can still applaud.
- **Mounted by wrapping `PTResponsive`, not inside a layout.** Each of `_desktop`/`_portrait`/`_landscape` is its own Stack, so that wrapper is the only point above all three — which is what "floats over the chat panel, banners, facecams, readiness overlay, control bar and the YouTube webview" requires. It sits in a **permanent** `IgnorePointer`: `Positioned.fill` hands down tight constraints, so even an empty overlay would eat every click on the video.
- **One shared ticker over a particle list**, capped at 14 with oldest-evicted; the ticker stops when the list empties (and restarts from zero, which is only safe *because* it stops exactly then). Compositions are preloaded at room entry and resolved **per frame**, not captured at spawn, so a reaction arriving mid-preload upgrades from the glyph fallback to the animation instead of staying flat for its whole life.
- **No `renderCache` on `RawLottie`.** The raster cache keys on the *global* rect, and the per-particle scale-in animates that — every frame would mint a fresh entry with a near-zero hit rate, on the one surface where video is playing.
- `RoomScreen` captures `sync.reactionsStream` **once** into a field: the getter hands out a fresh view object per call, so reading it inside `build` makes the overlay resubscribe every frame.
- **Strip motion follows the glass rule** — slide + scale, never fade. `Align(heightFactor:)` animates the slot alongside it, which is what stops portrait (where the strip sits in the column flow) from yanking the chat panel down on open. An open strip **pins the chrome** (`_scheduleControlsHide` bails on `_reactOpen`), and closes on the toggle, Esc, or a tap on the video.

### AV layer (`lib/av/`)

`LiveKitService` (per room): fetches a token from the `livekit-token` edge function, connects to `LIVEKIT_URL`, publishes mic/cam on toggle. Facecam tiles: `lib/rooms/widgets/facecam_rail.dart` (identity = Supabase user id).

Availability is `LiveKitService.isAvailableFor(room.avLevel)`, **not** `isConfigured` — a room whose tier grants `av_level: none` reuses the unset-`LIVEKIT_URL` path exactly (no service, no token fetch, no UI), so there is one hiding mechanism rather than two. `voice` keeps the mic and drops the camera toggle (`RoomControlBar.camAvailable`); `video` publishes capped at 360p/24fps, since a rail of up to 16 tiles is a thumbnail grid and the bandwidth belongs to what everyone came to watch.

### Analytics (`lib/analytics.dart`)

Product analytics to PostHog Cloud, so activation/retention/engagement and premium demand can be read off PostHog's built-in funnels rather than hand-built SQL. Configured-or-no-op like `lib/diagnostics.dart`: without `POSTHOG_API_KEY` there is no timer, no socket and no queue.

- **Deliberately not `posthog_flutter`.** That package has no reliable Windows support and Windows is a first-class release platform here; the HTTP API is ~100 lines of `dart:io` `HttpClient`, works on every target, keeps pubspec's exact pins untouched, and inherits `installTlsOverrides`' roots for free. Firebase Analytics (no desktop) and a hand-rolled Supabase events table (no ready-made funnel/retention UI) were both rejected — revisit only if the 1M events/mo free tier is exceeded.
- **Events are user-initiated only, and this is the invariant most likely to be broken by a well-meaning edit.** Never track inside `onRemote*` callbacks, gate-derived actions (`reason: 'gate'`), drift correction, `state_response`, or reconnect paths — eight clients would each report the same room action and every count would be multiplied by room size. It is the same distinction `SyncService.remoteActions` enforces for attribution toasts. Concretely: `media_selected` lives in `RoomScreen._handleModeSwitch`, **not** in `_switchToYouTubeMode`/`_switchToLocalMode`, because the remote `mode_switch` handler goes through those two. They keep only the per-client `_modesUsed` counter and the `playback_started` dedupe reset.
- **No ticks**, mirroring the `trace` rule: nothing per-frame, per-heartbeat, per-presence-sync, per-typing, per-scrub.
- **Privacy is a hard boundary.** Never send chat content, file names, file paths or YouTube URLs/ids. Media is reported as `kind` only. Room ids and user ids are fine. YouTube video ids were considered and deliberately excluded — ask the owner before adding them.
- **Failures are swallowed, always.** Analytics must never break the app it measures, so `flush` catches everything, re-queues the failed batch, and drops oldest past 500. A *persistent* delivery failure earns one `trace(category: 'analytics')` — never `reportNonFatal`, which would make a flaky network look like a bug.
- **`Analytics` is constructible (`Analytics()`) with a `static final instance`** so tests build their own rather than resetting a singleton, and `init` takes the key/host as *arguments* instead of reading `Env` — dotenv is unloaded under `flutter test`, and this keeps the `Env` read in `main.dart`. `init` also accepts a transport function, which is what lets `test/analytics_test.dart` cover batching, thresholds and retry without a socket.
- **Signed-out runs start on an anonymous distinct_id and alias via `$identify`/`$anon_distinct_id`.** Without that every signed-out `app_opened` would share one distinct_id and activation would read as a single person. A cold start that already has a Supabase session passes the real user id into `init` and never aliases.
- **Delivery is best-effort by design** — a 30 s timer or 20 queued events, plus a flush on `paused`/`hidden`/`detached` (desktop may never deliver `detached`). `onUpdaterBeforeQuitForUpdate` flushes with a **2 s cap** before `exit(0)`: that immediate exit is what stops the installer racing a live exe, so the queue only ever gets a bounded moment.
- **Tier events** are `room_extended` / `room_resumed` / `room_deleted` / `limit_hit {which}` / `upgrade_cta_shown` / `upgrade_cta_clicked {surface}`. `limit_hit` keeps the property name `which` that the shipped events already use — the newer plan text says `kind`, but a single event with two property names splits its own funnel. Surfaces so far: `room_expiry`, `room_limit`.
- **Opting out is a hard stop, and it is read before `init`.** `AnalyticsConsent` (shared_preferences) is loaded in `_bootstrap` *before* `Analytics.init`, so someone who opted out never emits even `app_opened`. `setOptedOut(true)` drops the queue and cancels the timer rather than filtering at the send point, and opting back in resumes from silence rather than replaying what was withheld. The toggle lives in the profile screen for guests and account holders alike. Release builds also only report once `POSTHOG_API_KEY` is in the `ENV_FILE` repo secret.

### Self-update (`lib/updates/`)

macOS and Windows replace themselves in place: `auto_updater` wraps Sparkle 2.9.3 and WinSparkle 0.8.1, fed by an `appcast.xml` the release workflow generates and attaches to every GitHub release. The app reads it through the permalink `releases/latest/download/appcast.xml`, which resolves to the newest **non-pre-release** — that exclusion is the feature, it's how `/release pre` ships something without pushing it at existing installs. There is no new hosting and no Apple Developer ID; the app stays ad-hoc signed and un-notarized, so **the archive signature is the entire trust anchor** and losing a private key strands every installed copy.

- **`supportsSelfUpdate` (`lib/platform.dart`), not `isDesktop`.** auto_updater has no Linux implementation and there are no Linux releases; every entry point into `lib/updates/` gates on the narrower getter.
- **Two key systems, because WinSparkle 0.8.1 has no EdDSA.** macOS is Sparkle's ed25519 (`SUPublicEDKey` in `macos/Runner/Info.plist`, signed by `macos/Pods/Sparkle/bin/sign_update` on the macOS runner); Windows is DSA-SHA1 over the *double* SHA-1 of the file (`windows/runner/resources/dsa_pub.pem`, wired up by the `DSAPub DSAPEM` line in `Runner.rc`, signed with plain openssl so the ubuntu release job can do it). Both `.pem`/`SUPublicEDKey` values are committed **public** keys — they look like generated build output but are not regenerable: replacing either orphans every install that shipped the old one. Private halves live only in the `SPARKLE_ED_PRIVATE_KEY` / `WINSPARKLE_DSA_PRIVATE_KEY` GitHub secrets and the user's password manager.
- **`.github/scripts/generate-appcast.sh` verifies both signatures against the committed public keys before publishing**, and fails the release if they disagree. That is the only moment the drift is catchable — nothing downstream checks, and an installed app rejects a bad download without ever telling anyone why. It also cross-checks the DMG's byte length against what was signed. Run it from the repo root with both artifacts in the cwd; it is directly runnable locally, which is how the failure paths were exercised.
- **The startup check is pure Dart and never touches the native updater** (`UpdateService.checkForUpdate`, unawaited from `_bootstrap`): HTTP GET the appcast, regex the newest advertised version, numeric-segment compare against `PackageInfo.version`. `compareVersions` exists because a string compare puts `0.10.0` *below* `0.9.0`; unparseable input deliberately reads as "not newer" so a malformed feed withholds the banner rather than nagging. Network-level failures (`SocketException`/`HandshakeException`/timeout) only `trace` — an offline laptop is the documented normal path, and reporting it is the noise the error doctrine warns about — while a bad status or an unparseable feed does `reportNonFatal`, because those mean updates are broken for everyone.
- **The native updater is initialised lazily, on the banner click, never at startup.** On Windows the plugin's `setFeedURL` calls `win_sparkle_init()`, and WinSparkle pops a native *"Check for updates automatically?"* dialog from the app's **second** launch onward (it writes `DidRunOnce` on the first and asks on the next) unless its `CheckForUpdates` config value is already set. The plugin never exposes `win_sparkle_set_automatic_check_for_updates`, so `_silenceWinSparkleOwnChecks` writes that value directly with `reg.exe` before the first init. **The registry path is derived from `Runner.rc`'s `CompanyName`/`ProductName`** (`HKCU\Software\app.synctogether\synctogether\WinSparkle`) — renaming either in the resource silently reintroduces the dialog. Failure there is reported and ignored: the cost is an extra prompt, not a broken update. macOS gets the same effect declaratively from `SUEnableAutomaticChecks=false`.
- **Windows must quit itself.** WinSparkle launches the installer and *then* calls the shutdown-request callback; its own default implementation does nothing, so `onUpdaterBeforeQuitForUpdate` calling `exit(0)` is what stops the installer racing a running exe. macOS needs no equivalent — Sparkle drives quit-and-relaunch itself.
- **The banner is lobby-only, and that is a correctness rule, not layout taste.** Updating quits the process; from inside a room that skips `leave_room` and strands the membership against the 8-member cap and authority election until the expiry sweep.
- **The affordance is a `PTBanner`** built by `_updateBanner()` in `lib/rooms/lobby_screen.dart`, dismissible for the session. `PTBanner`'s activity dots are now opt-in via `showActivity` rather than implied by `PTBannerKind.info` — the info tint carries both "working on it" (reconnecting) and plain information, and animated dots read as *waiting* on the latter. The lobby's `ListenableBuilder` merges `UpdateService` with `ProfileService`, so the banner participates in the same rebuild and can be conditionally absent from the `spacing:`-driven columns instead of leaving a dead gap.
- **The appcast is one shared file with a per-platform `<item>`.** Both readers filter on `sparkle:os`, which each reads **only as an `<enclosure>` attribute** — Sparkle ignores non-`macos` items outright, and WinSparkle looks for `windows` but *falls back to the first item in the feed* when nothing matches, so an untagged Windows enclosure would hand Windows users the DMG. `sparkle:version` compares against `CFBundleVersion` on macOS and the exe's VERSIONINFO `ProductVersion` on Windows; Flutter sets both to the bare pubspec version when there's no `+build` suffix, which is why one value serves every field.
- **`sparkle:installerArguments="/SILENT /SP- /NORESTARTAPPLICATIONS"`** drives the Inno installer. `/NORESTARTAPPLICATIONS` keeps Inno's Restart Manager out of the relaunch so exactly one thing owns it — the `Check: RelaunchAfterSilentInstall` entry that `patch-installer-script.ps1` appends. See that script's header for why the relaunch is a second entry rather than a rewrite of inno_bundle's `skipifsilent` one. One UAC prompt per update is accepted.
- **macOS re-prompts for camera/mic after every update, and always will** while the app is ad-hoc signed: TCC keys its grants on the code signature, and each ad-hoc build signs differently, so every self-update looks like a new app to it. This is not a one-off migration cost — it recurs per release, and the only fix is a Developer ID signature. Don't chase it in `lib/av/`.
- **`package_info_plus` is pinned back at 9.0.1**: 10.x needs win32 ^6, and `livekit_client` → `device_info_plus` 12.x pins win32 ^5. Bumping it fails resolution until LiveKit moves.
